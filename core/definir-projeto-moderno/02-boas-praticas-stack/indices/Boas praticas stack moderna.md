# Mercado define o pacote canônico

As definições modernas de mercado para TypeScript/Node.js, React, PostgreSQL, arquitetura e filas **já convergem com o pacote `beta-docs` do notinhas.shop**: monólito modular Express com módulos de feature e portas/adaptadores, TypeScript `strict`, PostgreSQL como fonte de verdade com índices e migrations online conscientes, Twelve-Factor (config em env, processos descartáveis, logs como stream), ADRs Nygard e C4 Context/Container, e um pacote de docs para IA em camadas (PRD → histórias Gherkin → contratos → ADRs → boas práticas). O achado central é que agentes devem tratar **`beta-docs/01`–`15` + `ia/CLAUDE.md` como contrato always-on** e **`referencias/` (103 espelhos oficiais)** como companheiros on-demand — nunca colar ASVS inteiro ou manuais longos no prompt. Onde o mercado empurra além do Beta atual — Server Components/Next como padrão operacional de React, BullMQ+Redis com outbox para side-effects assíncronos — o pacote já antecipa geocoding/scraping/e-mail em segundo plano e ports hexagonais, mas **ainda não congela worker+fila em ADR**; a ordem de leitura abaixo mapeia prática de mercado → documento canônico → espelho em `referencias/` para o agente fechar o gap sem reinventar a stack.

## TypeScript e Node fecham o backend do Beta

O mercado 2024–2026 trata o backend Node+TS como **contrato de toolchain + modularidade + operação**, não como framework único. Node.js documenta type stripping estável e recomenda `module: "nodenext"`, `erasableSyntaxOnly` e `verbatimModuleSyntax`, deixando explícito que o runtime **não** faz type-check ([Node.js TypeScript API](https://nodejs.org/api/typescript.html); [Running TypeScript Natively](https://nodejs.org/learn/typescript/run-natively)). TypeScript oficializa **`strict: true`** como família completa de checks ([TSConfig strict](https://www.typescriptlang.org/tsconfig/strict.html)) e proíbe hábitos que o Beta já barra em `08-boas-praticas-codigo.md` — `any` sem narrowing, boxed types, enums nativos quando union/`as const` basta ([TS Do’s and Don’ts](https://www.typescriptlang.org/docs/handbook/declaration-files/do-s-and-don-ts.html)). A Red Hat/IBM Node.js Reference Architecture fecha a opinião de produção: **`strict` + `isolatedModules`**, ship de JS compilado (não TS cru), validação runtime (ajv/Zod) porque tipos não validam input, Pino em stdout com redação de segredos, circuit breaker quando retries importam, containers multi-stage non-root com `CMD ["node",…]` ([RA TypeScript](https://github.com/nodeshift/nodejs-reference-architecture/blob/main/docs/development/typescript.md); [RA Logging](https://github.com/nodeshift/nodejs-reference-architecture/blob/main/docs/operations/logging.md); [docker-node BestPractices](https://github.com/nodejs/docker-node/blob/main/docs/BestPractices.md)).

No lado HTTP, Express oficializa `NODE_ENV=production`, Helmet/TLS via reverse proxy, queries parametrizadas, handlers de erro e **graceful SIGTERM** com readiness/liveness ([Express performance](https://expressjs.com/en/advanced/best-practice-performance/); [Express security](https://expressjs.com/en/advanced/best-practice-security/); [Express health/shutdown](https://expressjs.com/en/advanced/healthcheck-graceful-shutdown/)). Fastify reforça o anti-padrão de expor a app direto à internet e a validação na borda ([Fastify Recommendations](https://fastify.dev/docs/latest/Guides/Recommendations/)). NestJS Modules — mesmo sem adotar Nest no Beta ([ADR-003](../04-adrs.md#adr-003)) — é a articulação oficial mais clara de **feature module + exports como API pública + evitar `@Global()` como default** ([NestJS Modules](https://docs.nestjs.com/modules)). Isso mapeia 1:1 na árvore `modules/<feature>/{domain,application/ports,infra,http}` de `08-boas-praticas-codigo.md` e nos módulos C3 de `03-arquitetura.md`. **Inferência operacional para IA:** `tsc --noEmit` (e `npm run verify`) em CI; Zod na borda HTTP; Pino; Nginx como TLS; nunca tratar type stripping como substituto de type-check em produção.

## React moderno exige frontera server/client; o Beta escolhe PWA leve

Na era React 19, Server Components são a unidade padrão: renderizam ahead-of-time, não enviam o módulo ao browser, podem ser `async`, e só ganham interatividade compondo Client Components via **`'use client'`** — enquanto **`'use server'` marca Server Functions/Actions, não “arquivo Server Component”** ([react.dev Server Components](https://react.dev/reference/rsc/server-components); [Directives](https://react.dev/reference/rsc/directives)). O RFC 0188 fixou zero impacto de bundle no SC, acesso a dados no servidor, streaming com Suspense e preservação de estado cliente em refetch ([RFC 0188](https://github.com/reactjs/rfcs/blob/main/text/0188-server-components.md)). Next.js App Router é o **padrão operacional de mercado** mesmo para produtos “SPA-ish”: layouts/pages SC por default, `'use client'` só na folha interativa, fetch no servidor, composição por `children`/slots, checklist de produção (build+start, CWV, a11y lint, CSP, authz em cada Server Action) ([Next.js Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components); [Production checklist](https://nextjs.org/docs/app/guides/production-checklist)). Estado mínimo derivado no render, Effects só para sincronizar sistemas externos, testes via Testing Library com prioridade `getByRole` → `getByLabelText` (falha de role = possível falha de a11y) são regras agent-ready ([You Might Not Need an Effect](https://react.dev/learn/you-might-not-need-an-effect); [Testing Library Queries](https://testing-library.com/docs/queries/about/)).

**Alinhamento e tensão com o Beta:** `03-arquitetura.md` e `08` fixam **PWA mobile-first Vanilla/SPA** (Html5Qrcode, Leaflet, tokens `--nt-*`), não Next/RSC — decisão coerente com levesa mobile e ADR-001. Agentes devem aplicar as **regras de fronteira e a11y/testes** do mercado (sem `useEffect` para dados derivados; queries por role; sem hex solto) dentro da organização `features/` do Beta, e só importar o checklist Next/RSC se um ADR futuro migrar o shell para framework full-stack. Até lá, `12-prototipos.md` + tokens do DESIGN.md v2 são a fonte visual; `09-estrategia-de-testes.md` carrega a pirâmide e tags `@US-xx.yy`.

## PostgreSQL, monólito e filas formam a espinha operacional

PostgreSQL oficial manda **indexar só o que `WHERE`/`JOIN`/`ORDER BY` reais usam**, remover índices ociosos (custo de escrita + HOT), preferir B-tree, usar `CREATE INDEX CONCURRENTLY` em produção e montar índices concatenados left-to-right ([Indexes Intro](https://www.postgresql.org/docs/current/indexes-intro.html); [Index Types](https://www.postgresql.org/docs/current/indexes-types.html); [Use The Index, Luke!](https://use-the-index-luke.com/sql/where-clause/the-equals-operator/concatenated-keys)). Particionar só tabelas maiores que a RAM do servidor, com chave alinhada a filtro/retenção e sem explosão de partições em OLTP ([Table Partitioning](https://www.postgresql.org/docs/current/ddl-partitioning.html)). Isolamento default **`READ COMMITTED`** basta na maioria dos handlers Node; `SERIALIZABLE` exige retry em `40001`; MVCC evita bloquear leitores/escritores; locks longos e `ACCESS EXCLUSIVE` rotineiros são anti-padrão ([Transaction Isolation](https://www.postgresql.org/docs/current/transaction-iso.html); [MVCC](https://www.postgresql.org/docs/current/mvcc-intro.html); [Explicit Locking](https://www.postgresql.org/docs/current/explicit-locking.html)). Pooling: PgBouncer em modo `transaction` para alta concorrência se a app evitar features de sessão; `max_connections` modesto atrás do pooler ([PgBouncer Features](https://www.pgbouncer.org/features.html)). Migrations online: `NOT VALID` + `VALIDATE CONSTRAINT`, índice unique concurrente depois `USING INDEX`, evitar `ADD COLUMN` com default volátil que reescreve tabela ([ALTER TABLE](https://www.postgresql.org/docs/current/sql-altertable.html)). Bulk: `COPY`, depois índices, sempre `ANALYZE`; autovacuum ligado; `VACUUM FULL` não é rotina ([Populate](https://www.postgresql.org/docs/current/populate.html); [Routine Vacuuming](https://www.postgresql.org/docs/current/routine-vacuuming.html)). Isso amarra direto a `05-modelo-de-dados.md` (schema `enotas`, índices, constraints) e à regra de `08`/`13` de **não editar migration já aplicada**.

Arquiteturalmente, Twelve-Factor permanece baseline em 2024–2026 (open-source refresh; filosofia “surprisingly timeless”) — config em env, backing services (Postgres/Redis/SMTP), processos share-nothing, concorrência por tipo de processo, disposability/SIGTERM, logs como stream ([12factor.net](https://www.12factor.net/); [OSS announcement](https://www.12factor.net/blog/open-source-announcement)). Fowler/ThoughtWorks definem o default Beta: **modular monolith first**; microservices só após premium justificado ([Monolith First](https://www.martinfowler.com/bliki/MonolithFirst.html); [ThoughtWorks modular monolith](https://www.thoughtworks.com/en-us/insights/blog/microservices/modular-monolith-better-way-build-software)). Hexagonal (Cockburn/AWS) complementa módulos sem exigir rede ([Hexagonal](https://alistair.cockburn.us/hexagonal-architecture)). ADRs Nygard + C4 Context/Container são o mínimo documental compartilhado ([Nygard ADRs](https://cognitect.com/blog/2011/11/15/documenting-architecture-decisions); [C4 diagrams](https://c4model.com/diagrams)) — já materializados em `04-adrs.md` e `03`/`07`.

Para side-effects (geocode Nominatim, scrape SEFAZ, e-mail Mailcow), BullMQ de produção exige Redis com **AOF + `maxmemory-policy noeviction`**, handlers **idempotentes** sob at-least-once, workers com graceful `close()`, retries com backoff, sandbox para CPU-bound, e payload sem segredos ([Going to production](https://docs.bullmq.io/guide/going-to-production); [Idempotent jobs](https://docs.bullmq.io/patterns/idempotent-jobs); [Workers](https://docs.bullmq.io/guide/workers)). Dual-write DB+fila sem estratégia falha: **transactional outbox** (linha de negócio + outbox na mesma txn Postgres → relay → broker) com consumidores idempotentes ([microservices.io Outbox](https://microservices.io/patterns/data/transactional-outbox.html); [AWS Outbox](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/transactional-outbox.html)). **Gap explícito no pacote Beta:** `03` descreve geocodificação em segundo plano e scraping com timeout, e ADR de sessões descartou Redis para sessão JWT — mas **não há ADR Aceito para BullMQ/worker process**. Agentes devem implementar “segundo plano” via portas (`SefazScraperPort`, `NominatimClient`, `EmailClient`) e, antes de introduzir Redis de fila, abrir ADR alinhado a `14-operacao-deploy.md` e Twelve-Factor VIII/IX.

## Docs para IA: AGENTS.md fino, specs em camadas, OWASP como companheiro

O padrão aberto **AGENTS.md** (OpenAI → Linux Foundation AAIF) é o README-for-agents: Markdown livre, seções típicas (overview, build/test, style, security), precedência do arquivo mais próximo + override do chat do usuário ([agents.md](https://agents.md/); [OpenAI AAIF](https://openai.com/index/agentic-ai-foundation/)). Disciplina de tamanho (~**200 linhas** no alvo Claude; instruções concretas e path-scoped) e proibição de segredos no arquivo de instrução são o alavanca de aderência ([Claude Code memory](https://code.claude.com/docs/en/memory)). Spec-Driven Development moderno (spec-kit e equivalentes) é pipeline com gates humanos: specify → plan → tasks → implement, constitution com non-negotiables ([Spec-Kit workflow](https://sriaradhyula.github.io/posts/spec-kit-scaffolding-with-ai-coding-assistants/); [Turner SDD experiments](https://blog.luketurner.org/posts/experiments-with-spec-driven-development/)). A organização correta separa papéis: PRD (WHAT), SHALL com IDs, ADRs (WHY), OpenAPI (forma), Gherkin (prova executável) — Gherkin sozinho não congela arquitetura ([Beyond Gherkin](https://suherman.net/articles/beyond-gherkin-adr-shall-openapi)). Segurança always-on: banir secrets/PII em prompts/logs/commits; migrations autoradas não auto-executadas; destrutivos pedem humano; OWASP **Node + JS/TS Cheat Sheets** e **ASVS 5.0** como companheiros linkados, não colados no AGENTS ([OWASP Nodejs Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Nodejs_Security_Cheat_Sheet.html); [ASVS Index](https://cheatsheetseries.owasp.org/IndexASVS.html)).

O `beta-docs` já é esse pack: `01-prd` + `02-historias` (Gherkin) + `06-contratos` (Zod/REST como SoT de interface) + `04-adrs` + `08`/`09`/`10` + `13-guia-desenvolvimento-com-ia` + `ia/CLAUDE.md`/`prompts.md`. O fluxo `/task BETA-nnn` de `13` (contrato → testes Gherkin falhando → domínio → adaptadores → HTTP → UI → `npm run verify`) é SDD operacional sem precisar renomear pastas para `.specify/` no dia zero. **Regra de carregamento para agentes:** always-on = `ia/CLAUDE.md` + trechos de `08`/`10`/`06` da task; on-demand = US Gherkin + `05`/`07` + espelhos em `referencias/`; nunca dump de ASVS completo nem cupons fiscais reais no prompt.

## Conclusion

O pacote beta-docs do notinhas.shop **já é a materialização local das práticas de mercado** que uma IA precisa para desenvolver o sistema: contrato em camadas, monólito modular hexagonal-inspirado, TS strict, Postgres com integridade e migrations conscientes, e guia de agente com gates humanos. O valor novo desta síntese é a **disciplina de contexto** — always-on fino + `referencias/` on-demand — e o reconhecimento de que a próxima decisão arquitetural de mercado ainda em aberto no Beta é **formalizar (ou rejeitar explicitamente) worker + fila + outbox** para Nominatim/SEFAZ/Mailcow, em vez de deixar “segundo plano” implícito no mesmo processo HTTP.
